# dsh-service-manager

DeepSeek Harness 服务管理插件。设置页中，「服务管理」紧跟在「插件」下面。
登记后台进程和 Docker 容器，查询状态、手动停止或移除登记。

**仅手动停止。** 会话结束、插件卸载、Harness 退出都不会停止已登记的服务。
移除记录只修改登记文件，不停止进程、不停止或删除容器，也不删除数据卷。

## 安装

宿主版本要求：DSH >= 0.1.7（包括对应预发布版本）。

```sh
npx @deepseek-ai/dsh plugin --profile web add @guowenzhang/dsh-service-manager
```

来自 npm 官方源：<https://www.npmjs.com/package/@guowenzhang/dsh-service-manager>。装完重启宿主并刷新 Web 页面；本地目录开发安装、git 源与排查见 [AGENTS.md](AGENTS.md)。

桌面版：打开「插件 → 添加插件」，输入本地克隆路径，安装后选择「立即启用」。桌面 profile 由应用管理，不使用 CLI 安装。

## 使用

打开「设置 → 服务管理」。界面按「工作区 → 会话 → 服务」三层分组，工作区和会话可折叠，展示确认正在运行的服务。没有归属信息的服务归到「未关联工作区／未关联会话」。服务行提供「强制停止」，页面提供刷新、「全部关闭」和「显示已结束」开关。

点击服务的 HTTP(S) 地址，可在浏览器新标签页打开。会话行显示会话列表（左侧菜单）中的名称，并随名称变更更新；宿主未提供名称时退回缩短的会话 ID，悬停提示保留完整会话标识。带完整 Harness 会话标识的会话行还提供「打开会话」，点击后直接切换到该会话并关闭设置页；用户自己写的会话标签不能作为跳转目标。

打开「显示已结束」后，宿主已不再报告为运行中的记录会以灰显行列出，并标注「已退出」（登记的 PID 已关闭）、「PID 已被复用」（原进程已退出、PID 已属于其他进程）或「状态未知」（身份无法核验）。已结束的行不再提供停止操作，宿主返回的诊断信息放在悬停提示里。

「全部关闭」同样先弹窗确认，确认后对当前全部运行中的服务发送一次 `force: true` 批量请求，并列出未能关闭的服务。已结束和状态未知的记录不会进入批量请求。

分组兼容 Windows 路径大小写、斜杠和末尾分隔符差异。旧记录只填写工作区名称时，只有运行中的记录具有相同完整 Harness 会话 ID，且名称唯一匹配一个目录路径，才归入该目录；不同路径和有歧义的名称仍分开。分组不会改写登记文件或停止目标。

宿主自动收录资源，模型无需额外调用登记工具：

- **后台任务**：订阅 Harness 的 Bash／PowerShell 任务注册表，编译、开发服务等继承会话与工作区归属。插件启用前仍在运行的宿主任务也会列出。
- **独立进程**：通过 `shellEnv` 扩展写入归属标记，子进程自动继承。刷新时读取标记及创建时间，即使启动脚本已退出也能发现。Windows x64 和 Linux 支持此扫描；环境扫描仅返回本插件的归属标记，不记录其他环境变量。
- **本地 Docker／Compose**：本地非受限 Shell 执行中，自动安装并使用参数透传启动器。通过临时本地命名管道／Unix socket 转发 Docker API，仅给容器创建请求补充归属标签；不修改 Compose 文件或配置哈希。启动命令退出后，按标签恢复容器 ID 和归属。

任务采用宿主的实时状态和停止接口；发现的进程／容器身份保存到原登记文件，重复刷新不会重复登记。宿主任务的停止沿用 Harness 自己的终止策略。插件卸载只移除监听和启动钩子，不主动停止任何资源。

自动发现范围：新命令需要加载本版本后执行并保留继承的环境；清空环境、安装前已脱离运行且无归属标记的进程无法事后准确归属。Docker 自动标注支持 PATH 中的 `docker`／`docker.exe` 和命名上下文的本地 Unix socket／Windows pipe；绝对路径绕过启动器、远程 SSH/TCP Docker、自定义 `--config`、受限或远程执行器使用原命令，可手动登记。不需要 Docker 时不会改变 PATH。macOS/Windows ARM 的独立进程目前保留手动登记。

对于自动发现范围之外的资源，仍可通过插件的 `registerService` API 手动登记；不向模型提供登记工具：

- **进程**：输入 PID。插件自动读取创建时间，停止前再次核验。可勾选「手动停止时包含子进程」；默认只停止登记的进程。
- **容器**：输入名称、短 ID 或完整 ID，可指定 Docker 上下文。插件解析并保存完整容器 ID 和上下文，以后按该身份操作。
- 可附上项目、会话和 HTTP(S) 访问地址。

停止成功后服务从运行列表中消失，登记文件仍保留记录。状态无法确认、已退出或 PID 被复用的记录默认隐藏，打开「显示已结束」后才展示；这些记录不会被自动删除，也不会被当作原进程停止。刷新失败时隐藏过期列表并显示查询错误。API 仍提供完整状态列表和移除登记能力。

刷新只批量查询已登记的本机 PID 和手动停止后尚未退出的目标，同时查询容器状态。每次读取实时状态，不使用缓存；登记和准备手动停止时才查询完整进程树。

点击「强制停止」后弹窗确认，提供「取消」和「强制停止」，无需勾选。确认后直接发送 `force: true`，不尝试普通停止；取消不会停止服务。API 仍支持普通和强制停止：

- Windows 通过 API 普通停止时发送窗口关闭请求，控制台服务通常不支持此请求；页面则在确认后直接请求强制终止。PowerShell 失败仅返回文本诊断，不显示 CLIXML 或模块准备进度。
- Linux 正常停止发送 SIGTERM，强制停止发送 SIGKILL。
- Docker 正常停止使用无限宽限期，客户端最多等待 12 秒；超时后状态重新查询，必要时用户手动强制停止。Docker 停止请求可能仍在等待服务退出。
- 容器强制停止使用 `docker kill`。插件不改已有重启策略；重启策略可能使容器再次运行，界面状态详情包含策略名称。
- 包含子进程时，先核验当前进程树，按子进程先于父进程的顺序发送请求。部分停止后保存未退出子进程的身份，父进程退出后仍可继续手动停止；无法核验任一子进程则拒绝整棵树的停止。

「全部关闭」使用同样的确认弹窗，确认后对每个运行中的服务发送一次 `force: true` 请求，随后列出未能关闭的服务。只有存在运行中服务时才可用，且只由用户点击触发。

进程管理目前支持 Windows 和 Linux，Docker 管理需要宿主 PATH 中有 Docker CLI。
插件不会提权。若使用 DOCKER_HOST 环境变量连接 Docker，请创建并明确选择对应的命名上下文。
登记前已脱离父进程的服务需独立登记。
身份核验会减少 PID 复用风险；Linux 查询身份和发送信号之间仍存在操作系统级竞争窗口。

## 文件存储

默认文件：`$DSH_HOME/service-manager/services.json`，未配置 DSH_HOME 时为 `~/.dsh/service-manager/services.json`。
保存版本号、名称、归属信息、运行身份和未完成手动停止的目标；不保存运行状态、环境变量、命令行或密钥。
登记只观察已经存在的服务，不启动服务；没有自动启动、重新启动或自动清理。

更新在文件锁内重新读取文件，使用临时文件原子替换，支持多个 Harness 实例共享登记。
损坏 JSON、未知版本或不合法记录会明确报错，原文件不会被覆盖。
文件使用 0600、目录使用 0700（Windows 访问控制仍由系统 ACL 决定）。

配置可覆盖数据目录或文件，`file` 优先：

```yaml
config:
  dshHome: C:/Users/me/.dsh
  file: C:/Users/me/.dsh/service-manager/services.json
```

## 模型与插件接入

- 登记由宿主自动发现完成，已移除模型侧的 `service_register` 工具，避免模型继续选择手动登记。更新后需要重载插件或重启 Harness 才能更新工具列表，仅刷新浏览器不够；已有会话中的历史调用仍会保留。
- `service_list`：查询登记及实时状态。
- `service_stop`：按登记记录 UUID 手动停止；仅在用户要求停止时调用，强制停止须显式传 `force: true`。

其他插件可以通过 `ctx.get('serviceManager')` 调用 `registerService(request)`、`listServices({})`、`stopServices({ ids, force })`、`removeServices({ ids })`。
这些方法同时作为 `serviceManager` Typert Remote 提供给页面。接入服务管理不会替换其他插件已有的生命周期行为。
